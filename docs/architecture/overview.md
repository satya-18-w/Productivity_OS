# Architecture Overview

> Living document. It describes how Productivity OS is built as it stands today. The
> decisions and their rationale live in `docs/decisions/` (ADR-0001–0007); this file
> summarizes the shape and points at those ADRs. When this document and an ADR
> disagree, the ADR is authoritative and this file should be fixed.

## Architectural style

- **Modular monolith** — one codebase of internally-separated domain modules.
- **One Go application process** — the single deployable unit.
- **PostgreSQL** — the only datastore.
- **Single-origin production architecture** — the Go process serves both the JSON API
  and the built frontend assets.
- **No unnecessary distributed infrastructure** — no message broker, cache, search
  engine, queue, or second datastore. Adding any of these requires a new ADR recording
  a demonstrated need.

See ADR-0001.

## System shape

```
Browser
  → React + TypeScript + Vite SPA        (static assets served by the Go process)
    → Go HTTP server                     (stdlib net/http; middleware: request ID,
      → domain modules                    logging, panic recovery, authentication)
        → PostgreSQL                      (pgx / pgxpool)
```

**Request lifecycle.** The browser loads the SPA from the Go process and calls the
same-origin `/api`. Each API request passes through the middleware chain, which
attaches a request ID and — for authenticated routes — resolves the session cookie to
an `account_id` placed in the request context. A thin handler decodes and validates
the request at the boundary, calls its module's service (which owns any transaction),
which calls its store (generated query code over `pgx`). The handler writes a JSON
response, or the shared error envelope on failure.

## Dependency rule

Domain modules interact **only** through a single Go interface that each module exposes
at its package root. A module never imports another module's internal packages, reads
its tables, or shares its types. Modules are wired together in `cmd/server`. Direction:
`cmd/server` → domain modules → `internal/platform`; domain modules do not depend on
each other except through published interfaces. A violation is a defect, not a style
preference. See ADR-0002.

## Backend structure

At the architectural level:

- `cmd/server/` — process entry point: configuration loading and composition (wiring
  modules and shared infrastructure together).
- `internal/<domain>/` — one package per domain module, organized around a domain
  concept rather than a technical layer. Each exposes one interface as its public
  surface.
- `internal/platform/` — shared infrastructure with no business logic: database pool,
  configuration, clock, timezone/date helpers, shared HTTP helpers.
- Within a module, `handler → service → store` where that separation earns its place:
  the handler adapts HTTP, the service holds behaviour and transaction boundaries, the
  store holds data access. Avoid abstraction a module does not need — no
  repository-interface indirection until there is a second implementation.

The concrete module list is not designed up front; modules are introduced by milestone
specifications. See ADR-0002; layering idioms live in `conventions.md`.

## Persistence

PostgreSQL, accessed through `pgx` / `pgxpool`. Query code is generated by `sqlc` from
explicit hand-written SQL — no ORM. Schema changes are forward-only migrations in a
single directory. Each writing use-case runs in one transaction owned by the service
layer; reads use the pool directly. See ADR-0003 for rationale and alternatives.

## Time and timezone

Each account carries an IANA time-zone name. Every instant is stored as `timestamptz`;
the server process runs in UTC. All calendar reasoning — which date or ISO week an
instant belongs to, and the bounds of a date or range in the account's zone — is
centralized in one `internal/platform` timezone package, and time-bounded queries
filter by an instant range computed there. No `AT TIME ZONE` scattered through SQL. See
ADR-0005. The product questions about default zone (Q4), overlap totals (Q7), and
future-dated records (Q9) are resolved in milestone specs, not here.

## Authentication and isolation

- **Server-side sessions.** On login the server stores a session row in PostgreSQL and
  returns an opaque, high-entropy token in an `HttpOnly`, `Secure` cookie. No JWT.
- **Argon2id** is the password-hashing algorithm.
- **Account-scoped persistence.** Every query over account-owned data is scoped by
  `account_id`, and that `account_id` is derived **only** from the authenticated
  session — never from request input.
- **Mandatory cross-account isolation tests** for every module that owns account data
  (verifying requirement N3).
- **Row-Level Security is excluded from V1**; isolation is enforced at the application
  layer plus those tests.

**Deferred to the M1 authentication specification:** session lifetime and idle
timeout, the CSRF protection mechanism, login rate limiting, the password policy
(product question Q6), and the concrete Argon2id parameters. See ADR-0004.

## API

- JSON over HTTP, resource-oriented, all endpoints under `/api` (no version segment;
  additive changes only).
- Built on the standard library `net/http`; no web framework.
- Validation happens at the application boundary and returns **structured, field-level
  validation errors**.
- Every error response uses one **custom error envelope** — `error.code`,
  `error.message`, optional `error.fields` — with the appropriate HTTP status
  (400 / 401 / 403 / 404 / 409 / 500).
- **500 responses never expose internal implementation details, database errors, stack
  traces, or secrets**; detail is logged server-side only.

See ADR-0002.

## Frontend

React + TypeScript + Vite, built as a static single-page application with client-side
routing. No server-side rendering and no Next.js — the app is authenticated with no
SEO surface. In production the static assets are served by the Go process, so the
browser talks to a same-origin API with no CORS layer.

**Deferred:** the asset-packaging mechanism (`go:embed` vs. files alongside the
binary), the data-fetching approach, and all styling/component libraries. See ADR-0006.

## Cross-cutting concerns

- **Structured logging** via the standard library, applied as middleware.
- **Configuration** from the environment, loaded at startup.
- **Request IDs** attached by middleware and carried through logs.
- **Panic recovery** middleware that converts a panic into a generic 500 in the shared
  error envelope.
- **Account scoping** on every account-owned read and write (see Authentication and
  isolation).
- **Deterministic behaviour** — no AI, prediction, or heuristics in V1.

Implementation idioms for these live in `conventions.md`, not here.

## Modules

Concrete modules are introduced by milestone specifications as each milestone is
planned. Each exposes one interface at its package root; they are wired in `cmd/server`.

| Module | Owns | Published interface | Depends on (via interface) |
|--------|------|---------------------|----------------------------|
| `internal/account` | accounts, sessions, auth + CSRF middleware | `account.Service` | — |
| `internal/categories` | `categories` table (name, colour, icon, archive) | `categories.Service` | — |
| `internal/timeline` | `time_blocks` + per-date timeline / comparison views | `timeline.Service` | `account` (zone), `categories` (`CategoryStore`) |
| `internal/tasks` | `tasks` + state transitions | `tasks.Service` | — *(gains `categories` in MX1 Phase 3)* |
| `internal/habits` | `habits` + completions, streaks | `habits.Service` | `account` (zone) *(gains `categories` in MX1 Phase 3)* |
| `internal/goals` | `goals` + progress | `goals.Service` | — *(gains `categories` in MX1 Phase 3)* |

`categories` was extracted from `timeline` in MX1 (ADR-0009): it is a shared,
cross-cutting concept, so every module that assigns a `category_id` validates it
through a small `AssignableToAccount` interface wired to `categories.Service`.
Per-category item counts are composed in `cmd/server` (`categories.Counter` per
module), never inside `categories` — it stays pure to its own table.

## Build, test and local development

- **Docker Compose runs only PostgreSQL**; Go and the frontend toolchain run natively
  on the host.
- A **`Makefile`** provides the entry points (database up/down, migrate, run, test,
  lint, `sqlc`).
- Tests use the Go standard library `testing` package with `testify/require` for
  assertions: unit tests for pure logic, **integration tests against a real
  PostgreSQL**, and **mandatory cross-account isolation tests**.
- **GitHub Actions** verifies every push and pull request (build, vet, lint, tests
  with a PostgreSQL service, `sqlc` freshness, frontend typecheck/build). CI does not
  deploy.
- **Browser end-to-end tests** are decided per milestone, where acceptance benefits
  from real-browser verification — not established or excluded globally.

See ADR-0007.

## Deployment

Approved **shape** only:

- A **single application deployment unit** — the Go process.
- That process **serves both the API and the frontend assets**.
- **PostgreSQL** as the datastore.
- **Single origin** for the browser.

Not selected, and out of scope until a deployment spike:

- the production **hosting provider**;
- the **database provider**;
- the **backup mechanism** (a backup and a tested restore are required before V1 is
  done — requirement N6 — but how is undecided);
- the exact **frontend asset-packaging** mechanism.

ADR-0008 will record the hosting/deployment decision after that spike.

## Decided vs deferred

**Decided** (see the referenced ADR):

| Area | ADR |
|------|-----|
| Modular monolith, single deployment unit, single origin, no distributed infra | ADR-0001 |
| Go single module, stdlib `net/http`, module structure & dependency rule, `/api` contract, validation stance, error envelope | ADR-0002 |
| PostgreSQL via `pgx`/`pgxpool`, `sqlc`, forward-only migrations, service-owned transactions | ADR-0003 |
| Server-side sessions, `HttpOnly` cookie, Argon2id, application-layer account isolation, no RLS in V1 | ADR-0004 |
| IANA timezone per account, `timestamptz`, UTC server, centralized date/week bucketing | ADR-0005 |
| React + TypeScript + Vite static SPA, no SSR, same-origin serving | ADR-0006 |
| Compose-for-Postgres local dev, `Makefile`, real-Postgres integration + isolation tests, GitHub Actions, per-milestone E2E | ADR-0007 |

**Deferred** (meaningful decisions still open):

- Production hosting provider, database provider, and backup mechanism — ADR-0008,
  after a spike.
- Frontend asset-packaging mechanism (`go:embed` vs. adjacent files).
- Frontend data-fetching approach and styling/component libraries.
- M1 authentication details: session lifetime/idle timeout, CSRF mechanism, login rate
  limiting, Argon2id parameters.
- Password policy — product question Q6.
- Time-behaviour product questions Q4, Q7, Q9.
- Whether raw `pgx` or another approach is used for any genuinely dynamic query
  (evaluated per case).
