# Productivity OS — V1 Requirements

> Status: approved. This document defines the scope of V1. Feature SPECs are written
> against it. It states what a user can observe and do — not how it is built. No
> schemas, endpoints, or UI layouts appear here.

## V1 thesis

An authenticated user can plan a day as time blocks, record what actually happened,
manage tasks on a fixed four-column Kanban board, keep daily habits with streaks,
define goals, complete structured daily and weekly reviews, export all of their data,
and view a fixed set of deterministic reports about where their time went — with no AI,
no collaboration, and no recurring-task automation.

## Core domain concepts and their relationships

- An **account** owns everything below. No data is visible or reachable across accounts.
- A **category** is a flat, user-defined label. A time block may reference zero or one
  category. Tasks, habits, and goals carry no category in V1.
- A **time block** has a start instant, an end instant strictly after the start, and an
  optional category. It is either **planned** or **actual** — a fixed attribute set
  when the block is created and never changed afterwards. A block may span midnight.
  Blocks may overlap; the product neither prevents nor flags overlap.
- A **day plan** is all planned blocks whose date is a given calendar date in the
  account's timezone.
- A **task** has a title, an optional description, an optional due date, and exactly one
  **state**: `BACKLOG`, `TODO`, `IN_PROGRESS`, or `DONE`.
- The **board** is all of the account's tasks grouped by state into four fixed columns
  in the order `BACKLOG` → `TODO` → `IN_PROGRESS` → `DONE`.
- A **habit** has a name and is either active or archived. For each calendar date a
  habit is either completed or not completed. A **streak** is the number of consecutive
  completed dates whose most recent day is today or yesterday (account timezone).
- A **goal** has a title, an optional description, an optional target date, and a
  manually set progress state.
- A **daily review** belongs to one calendar date. A **weekly review** belongs to one
  ISO week. Each is a set of free-text answers to a fixed list of prompts.
- A **report** is a read-only aggregation over a date range. Reports never write data.

## Functional requirements

Each area lists observable capabilities and one explicit **scope boundary**.

### 1. Account and authentication

- The user can create an account with an email address and a password.
- The user can log in and log out.
- The user can set their timezone; it is given a value at account creation and can be
  changed later.
- A logged-in user sees only their own data everywhere in the application.
- The user can change their password while logged in.

**Scope boundary:** No email verification, no password-reset email, no OAuth or social
login, no multi-factor authentication, no self-service account deletion. No profile
fields beyond email, password, and timezone. One account per person; no account
switching or linking.

### 2. Categories

- The user can create a category with a name.
- The user can rename a category.
- The user can archive a category so it is no longer offered when assigning one,
  without changing blocks already assigned to it.
- The user can see their list of active categories.

**Scope boundary:** Flat list only — no parent/child, no groups. No colour or icon
carries product meaning (a frontend may show a colour; nothing depends on it). No
merging categories. No hard delete. No per-category time targets or budgets.

### 3. Day planning (planned blocks)

- The user can add a planned block for a chosen date with a start time, an end time
  after the start, and an optional category.
- The user can edit a planned block's start, end, and category.
- The user can delete a planned block.
- The user can view all planned blocks for a chosen date on that date's timeline.
- The user can create a planned block that ends on the following calendar date.

**Scope boundary:** No templates, no "copy a day", no recurring plans. Planned blocks
are created one at a time. Overlaps are allowed and not prevented. Planning is for a
single date at a time; no multi-day planning view.

### 4. Activity logging (actual blocks)

- The user can record an actual block with a start time, an end time after the start,
  and an optional category.
- The user can edit an actual block's start, end, and category.
- The user can delete an actual block.
- The user can record an actual block that crosses midnight.
- Recording an actual block never requires referencing a planned block.

**Scope boundary:** No live timer or stopwatch — a block is entered with explicit start
and end times. No automatic capture from any source. No "convert plan to actual".
Overlaps are allowed and not flagged.

### 5. Timeline view

- The user can view a chosen date's timeline showing that date's blocks positioned
  against the hours of the day.
- The user can view planned and actual blocks for the same date together, visually
  distinguishable.
- The timeline correctly places a block that starts on the chosen date and ends on the
  next.

**Scope boundary:** One date at a time; no week or month timeline. Visual granularity
(e.g. 15-minute rows) is a frontend choice, not a requirement. No editing gestures are
required on the timeline beyond what sections 3 and 4 already provide.

### 6. Planned vs actual comparison

- For a chosen date, the user can see total planned time and total actual time per
  category.
- For a chosen date, the user can see the difference between planned and actual time
  per category.

**Scope boundary:** Comparison is by per-category totals for a single date. No
block-to-block matching, no adherence score, no streak of well-planned days.
Deterministic arithmetic only.

### 7. Tasks

- The user can create a task with a title, and optionally a description and a due date.
- The user can edit a task's title, description, and due date.
- The user can change a task's state to any of `BACKLOG`, `TODO`, `IN_PROGRESS`,
  `DONE`, in any direction.
- The user can delete a task.
- The user can see all of their tasks.

**Scope boundary:** No recurring tasks (see V2). No subtasks, checklists, priorities,
labels, estimates, attachments, or comments. No assignee. The due date is a plain date
with no time and no reminder. No dependencies between tasks.

### 8. Kanban board

- The user can view all tasks arranged into four columns — `BACKLOG`, `TODO`,
  `IN_PROGRESS`, `DONE` — in that fixed order.
- The user can move a task from any column to any other column, which sets its state.
- The board reflects task creation, edits, and deletion from section 7.

**Scope boundary:** Columns are fixed and map exactly to the four task states. The user
cannot create, rename, reorder, or delete columns. One board per account. No WIP
limits, swimlanes, filters, or saved views. Task ordering within a column is not a
product requirement in V1.

### 9. Habits and streaks

- The user can create a habit with a name.
- The user can mark a habit completed for a specific date, and unmark it.
- The user can archive a habit and unarchive it.
- The user can see, for each active habit, its current streak.
- The user can see, for a chosen date, which habits were completed.

**Scope boundary:** Daily cadence only — every habit means "do it every day". No weekly
targets, weekday selection, monthly habits, or "X times per week". A streak counts
consecutive completed dates whose most recent day is today or yesterday; one missed
date resets the streak to zero; there are no grace days, freezes, or vacation modes. A
completion has no quantity, partial value, or note. No reminders.

### 10. Goals

- The user can create a goal with a title, and optionally a description and a target
  date.
- The user can edit a goal's title, description, and target date.
- The user can set a goal's progress state to one of: not started, in progress,
  achieved, abandoned.
- The user can see their list of goals with progress state.
- The user can delete a goal.

**Scope boundary:** Progress is one of four states, set manually — no percentage, no
numeric target, no progress derived from tasks, habits, or time. A goal is not linked
to any other entity in V1. No milestones, key results, or check-in history.

### 11. Daily review

- The user can complete a daily review for a chosen date by answering a fixed set of
  prompts with free text.
- The user can edit a previously completed daily review.
- The user can view a past daily review.
- While completing a daily review, the user can see that date's totals — actual time
  per category, and which habits were completed — for reference.

**Scope boundary:** One fixed prompt set, defined in the review SPEC, not editable by
the user. Answers are free text only — no ratings, scores, or structured fields. The
reference data is display-only. A review produces no follow-up actions or carry-over
items.

### 12. Weekly review

- The user can complete a weekly review for a chosen ISO week by answering a fixed set
  of prompts with free text.
- The user can edit and view a past weekly review.
- While completing a weekly review, the user can see that week's totals — actual time
  per category, habit completion counts, and the number of tasks that entered `DONE`
  that week — for reference.

**Scope boundary:** As for the daily review — one fixed non-editable prompt set,
free-text answers, display-only reference data, no generated output. Week boundaries
follow the ISO week resolved in the account's timezone.

### 13. Reports

The user can view each of the following reports over a user-chosen date range,
computed deterministically:

- **Time by category** — total actual time per category.
- **Planned vs actual by category** — planned total, actual total, and difference per
  category.
- **Habit completion** — for each habit, the number of completed days and the
  completion rate across the range.
- **Task throughput** — the number of tasks that entered `DONE` within the range.
- **Daily actual totals** — total actual time for each day in the range.

**Scope boundary:** This list is exhaustive for V1. No custom report builder, no
arbitrary group-by, no saved reports, no comparison between two ranges, no trend lines
or forecasts, no correlation between metrics. A frontend may render these as charts;
the underlying figures are fixed.

### 14. Data export

- The user can export all of their data — categories, planned blocks, actual blocks,
  tasks, habits and their completions, goals, daily reviews, and weekly reviews — in a
  single open, documented format, without contacting support.

**Scope boundary:** Export is a full, user-initiated snapshot delivered as a download.
No scheduled export, no partial or filtered export, no import in V1, no delivery to a
third-party destination.

## Non-functional requirements

### N1 — Architecture

A single deployable Go binary (modular monolith). PostgreSQL is the only datastore. No
message broker, cache, or search engine in V1.

### N2 — Cost

The deployed system, including database and hosting, runs within free tiers at the
expected load: on the order of tens of accounts, each with thousands of blocks, tasks,
and completions.

### N3 — Data isolation

Every read and write is scoped to the authenticated account. No interface the product
exposes lets one account observe or modify another account's data.

### N4 — Time and timezone correctness

Every instant is stored unambiguously. "A date" and "a week" are always resolved in the
account's timezone. Blocks that span midnight, and reports whose range crosses a
daylight-saving transition, produce correct totals.

### N5 — Web client

A modern web frontend, usable across current desktop and mobile browser viewport sizes
(responsive). No native mobile app, no offline mode, no installable-PWA requirement in
V1.

### N6 — Availability and durability

Best-effort availability appropriate to a personal tool on free infrastructure.
Regular database backups exist, and a restore has been performed successfully at least
once before V1 is considered done.

### N7 — Performance

Interactive views — a day's timeline, the board, a report over a one-month range —
respond within a small fraction of a second at the expected load. No numeric SLO beyond
"feels immediate for one user".

## V1 non-goals (explicit)

Deliberately excluded from V1. Items marked → V2 or → V3 are placed on the roadmap; the
rest have no committed home.

- Recurring tasks and any recurrence/scheduling engine → **V2**
- Reusable day-plan templates and "copy a previous day" → **V2**
- Importing time or events from an external calendar (e.g. Google Calendar) → **V2**
- Live timer / stopwatch capture of actual time → **V2 (candidate)**
- A wider or customizable analytics set; a custom report builder → **V2**
- AI-assisted planning, suggested schedules, pattern detection, recommendations → **V3**
- Auto-categorization or any "smart" default → **V3**
- Weekly / monthly / weekday-selective habit cadences; grace days; streak freezes → not committed
- Numeric or automatic goal progress; goals linked to tasks, habits, or time → not committed
- Editable review prompt sets; ratings or scores in reviews → not committed
- Task subtasks, priorities, labels, estimates, attachments, comments, dependencies → not committed
- Configurable Kanban columns; multiple boards; WIP limits; swimlanes → not committed
- Category hierarchy, groups, meaningful colours, merging, per-category budgets → not committed
- Email verification, password-reset email, OAuth / social login, MFA, self-service account deletion → not committed
- Any collaboration, sharing, teams, accountability, or social feature → **permanent non-goal** (see Vision)
- Native mobile app, offline mode, PWA install → not committed
- Notifications, reminders, email digests → not committed
- Data import; scheduled or partial export → not committed
- Real-time multi-device sync; websockets → not committed
