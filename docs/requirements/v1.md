# Productivity OS — V1 Requirements

> Status: approved. This document defines the scope of V1. Feature SPECs are written
> against it. It states what a user can observe and do — not how it is built. No
> schemas, endpoints, or UI layouts appear here.

## V1 thesis

An authenticated user can plan a day as time blocks, record what actually happened,
manage tasks on a fixed four-column Kanban board, keep daily habits with streaks,
define goals, capture free-form notes, complete structured daily and weekly reviews,
export all of their data, and view a fixed set of deterministic reports about where
their time went — with no AI, no collaboration, and no recurring-task automation.

## Core domain concepts and their relationships

- An **account** owns everything below. No data is visible or reachable across accounts.
- A **category** is a flat, user-defined label with a colour and an icon. Time blocks,
  tasks, habits, and goals (and, once built, calendar events) may each reference zero
  or one category. *(Amended 2026-09-04 with ADR-0009 — originally categories were
  time-block-only with no meaningful colour/icon.)* Notes do **not** carry a category
  (MX4) — the reference screen's own "tags vs. categories" ambiguity is resolved by not
  building either for notes in V1.
- A **time block** has a start instant, an end instant strictly after the start, and
  either an optional category **or** an optional link to a task, never both. It is
  either **planned** or **actual** — a fixed attribute set when the block is created
  and never changed afterwards. A block may span midnight. Blocks may overlap; the
  product neither prevents nor flags overlap. *(Amended 2026-09-05, task/time-block
  linkage — a task-linked block inherits the task's category rather than carrying its
  own; a block with no linked task behaves exactly as before.)*
- A **day plan** is all planned blocks whose date is a given calendar date in the
  account's timezone.
- A **task** has a title, an optional description, an optional due date, an optional
  **priority** (`HIGH`, `MEDIUM`, or `LOW`; added 2026-09-05), exactly one
  **state**: `BACKLOG`, `TODO`, `IN_PROGRESS`, or `DONE`, and zero or more linked time
  blocks. *(Amended 2026-09-05 — block linkage added; a task's other fields never
  derive from or propagate to a linked block, and vice versa.)*
- The **board** is all of the account's tasks grouped by state into four fixed columns
  in the order `BACKLOG` → `TODO` → `IN_PROGRESS` → `DONE`.
- A **habit** has a name, an optional target descriptor, and is either active or
  archived. For each calendar date a habit is either completed or not completed. A
  **streak** is the number of consecutive completed dates whose most recent day is
  today or yesterday (account timezone). *(Amended 2026-09-04, MX3 — target descriptor
  added; still display-only, the completion model is unchanged.)*
- A **goal** has a title, an optional description, an optional target date, a manually
  set progress state, and zero or more linked tasks. A goal's **derived progress** is
  the fraction of its linked tasks in state `DONE`. *(Amended 2026-09-04, MX3 — task
  linkage and derived progress added; the manual progress state is unchanged and
  independent of the derived figure.)*
- A **daily review** belongs to one calendar date. A **weekly review** belongs to one
  ISO week. Each is a set of free-text answers to a fixed list of prompts.
- A **report** is a read-only aggregation over a date range. Reports never write data.
- A **note** has a title and a free-text body. It is not linked to any task, habit,
  goal, or category. *(Added 2026-09-05, MX4.)*

## Functional requirements

Each area lists observable capabilities and one explicit **scope boundary**.

### 1. Account and authentication

- The user can create an account with an email address and a password.
- The user can log in and log out.
- The user can set their timezone; it is given a value at account creation and can be
  changed later.
- A logged-in user sees only their own data everywhere in the application.
- The user can change their password while logged in.

**Scope boundary:** No email verification, no password-reset email, no OAuth or social
login, no multi-factor authentication, no self-service account deletion. No profile
fields beyond email, password, and timezone. One account per person; no account
switching or linking.

### 2. Categories

*(Amended 2026-09-04 with ADR-0009. Originals: categories applied only to time blocks
and had no meaningful colour/icon.)*

- The user can create a category with a name, a colour, and an icon.
- The user can rename a category and change its colour and icon.
- The user can archive a category so it is no longer offered when assigning one,
  without changing items already assigned to it.
- The user can see their list of active categories, each with how many time blocks,
  tasks, habits, and goals it currently labels.
- A category may be assigned to a time block, a task, a habit, or a goal — zero or one
  category per item.

**Scope boundary:** Flat list only — no parent/child, no groups. Colour and icon are a
key/name chosen from a fixed set; the backend does not interpret a colour value. No
merging categories. No hard delete. No per-category time targets or budgets. A category
is not required on any item.

### 3. Day planning (planned blocks)

- The user can add a planned block for a chosen date with a start time, an end time
  after the start, and an optional category.
- The user can add a planned block that references a task instead of being
  categorized directly — a task-linked block always shows the task's own category,
  never a separately chosen one. *(Added 2026-09-05, task/time-block linkage.)*
- The user can edit a planned block's start, end, category, and task link.
- The user can delete a planned block.
- The user can view all planned blocks for a chosen date on that date's timeline.
- The user can create a planned block that ends on the following calendar date.

**Scope boundary:** No templates, no "copy a day", no recurring plans. Planned blocks
are created one at a time. Overlaps are allowed and not prevented. Planning is for a
single date at a time; no multi-day planning view. A block may reference **at most
one** task; a task may have any number of linked blocks (planned or actual). A
task-linked block cannot also carry its own category — setting both on the same
block is rejected, not silently resolved (§10's inheritance rule applies).

### 4. Activity logging (actual blocks)

- The user can record an actual block with a start time, an end time after the start,
  and an optional category.
- The user can record an actual block that references a task instead of being
  categorized directly, with the same inheritance rule as planned blocks.
  *(Added 2026-09-05, task/time-block linkage.)*
- The user can edit an actual block's start, end, category, and task link.
- The user can delete an actual block.
- The user can record an actual block that crosses midnight.
- Recording an actual block never requires referencing a planned block.

**Scope boundary:** No automatic capture from any source. No "convert plan to actual".
Overlaps are allowed and not flagged. Linking a block to a task never changes the
task's state, and moving a task's state never touches any block — the link is a pure
reference with no state propagation in either direction.

**Focus timer (Added 2026-09-05, product owner).** The Timeline (Day) screen may offer
a standalone focus-session timer (a fixed set of preset durations — e.g. a 25-minute
session and short/long breaks — start/pause, a visible countdown). It is a plain
countdown with no persistence and no effect on any other data: finishing, pausing, or
resetting a session never creates, edits, or logs a time block, and the timer does not
read or write any account data. This does not reopen "no live timer or stopwatch" for
*blocks* — a block is still always entered with explicit start and end times; the timer
and the block model remain unconnected.

### 5. Timeline view

- The user can view a chosen date's timeline showing that date's blocks positioned
  against the hours of the day.
- The user can view planned and actual blocks for the same date together, visually
  distinguishable.
- The timeline correctly places a block that starts on the chosen date and ends on the
  next.

**Scope boundary:** Visual granularity (e.g. 15-minute rows) is a frontend choice, not a
requirement. No editing gestures are required on the timeline beyond what sections 3
and 4 already provide. A task-linked block's category shown on the timeline is always
the linked task's category (§3/§4/§10) — the timeline never displays a stale or
independently-set category for such a block, because none can exist.

**Week and month timeline (Amended 2026-09-05, product owner — originally: "one date at
a time; no week or month timeline").** The user can also view a chosen ISO week, or a
chosen calendar month, as a timeline of that period's blocks — the same planned/actual
data as the Day view, laid out over more days at once. This is a different rendering of
the same block data (§3, §4) and creates no new data or fields: no per-day totals row,
no cross-day aggregation beyond what §6 already defines, no dashboard-style widgets
(KPIs, donuts, "insights") on these views — those remain excluded for the reasons
already recorded in `design-system.md §6.4` (P3, P6, VP3), which this amendment does
not reopen.

### 6. Planned vs actual comparison

- For a chosen date, the user can see total planned time and total actual time per
  category.
- For a chosen date, the user can see the difference between planned and actual time
  per category.

**Scope boundary:** Comparison is by per-category totals for a single date. No
block-to-block matching, no adherence score, no streak of well-planned days.
Deterministic arithmetic only. A task-linked block's time counts toward its linked
task's category, not "Uncategorized" — comparison and every §13 report that totals
time by category resolve a task-linked block's category through its task before
bucketing (§10).

### 7. Tasks

- The user can create a task with a title, and optionally a description, a due date,
  and a priority. *(Priority added 2026-09-05, MX3-follow-up.)*
- The user can edit a task's title, description, due date, and priority.
- The user can change a task's state to any of `BACKLOG`, `TODO`, `IN_PROGRESS`,
  `DONE`, in any direction.
- The user can delete a task.
- The user can see all of their tasks.
- A task may have zero or more linked time blocks (planned or actual); deleting a
  task clears the link on its blocks rather than deleting them or blocking the
  delete. *(Added 2026-09-05, task/time-block linkage.)*
- The user can see all of a task's linked time blocks (planned and actual, across
  any date). *(Added 2026-09-05 — reverses the original MX-TL scope call below,
  once a concrete frontend need for it appeared: viewing a task and seeing when
  it's scheduled.)*

**Scope boundary:** No recurring tasks (see V2). No subtasks, checklists, labels,
estimates, attachments, or comments. No assignee. The due date is a plain date with no
time and no reminder. No dependencies between tasks. Priority is one of `HIGH`,
`MEDIUM`, `LOW`, or unset — it is purely a label the user sets and reads back, with no
effect on ordering, board layout, or any other behaviour. *(Added 2026-09-05,
product-owner approved: priority only — a starred/pinned flag and a time-of-day due
were asked about in the same round and were not approved; they remain out of scope.)*
No block state (planned/actual, done-ness) is derived from or propagated to a task,
and no task field is derived from or propagated to a block — the list of a task's
blocks is a plain read, not a computed status.

### 8. Kanban board

- The user can view all tasks arranged into four columns — `BACKLOG`, `TODO`,
  `IN_PROGRESS`, `DONE` — in that fixed order.
- The user can move a task from any column to any other column, which sets its state.
- The board reflects task creation, edits, and deletion from section 7.

**Scope boundary:** Columns are fixed and map exactly to the four task states. The user
cannot create, rename, reorder, or delete columns. One board per account. No WIP
limits, swimlanes, filters, or saved views. Task ordering within a column is not a
product requirement in V1.

### 9. Habits and streaks

- The user can create a habit with a name and an optional target descriptor (free
  text, e.g. "30 minutes", "8 glasses", "At least 20 pages"). *(Added 2026-09-04,
  MX3.)*
- The user can edit a habit's target descriptor.
- The user can mark a habit completed for a specific date, and unmark it.
- The user can archive a habit and unarchive it.
- The user can see, for each active habit, its current streak.
- The user can see, for a chosen date, which habits were completed.

**Scope boundary:** Daily cadence only — every habit means "do it every day". No weekly
targets, weekday selection, monthly habits, or "X times per week". A streak counts
consecutive completed dates whose most recent day is today or yesterday; one missed
date resets the streak to zero; there are no grace days, freezes, or vacation modes. A
completion has no quantity, partial value, or note — the target descriptor lives on the
habit, not the completion, and is never validated or enforced against a completion; it
is retained purely for the user's own reference. No reminders.

### 10. Goals

- The user can create a goal with a title, and optionally a description and a target
  date.
- The user can edit a goal's title, description, and target date.
- The user can set a goal's progress state to one of: not started, in progress,
  achieved, abandoned.
- The user can see their list of goals with progress state.
- The user can delete a goal.
- The user can link a task to a goal, and unlink it. *(Added 2026-09-04, MX3.)*
- The user can see, for each goal, its derived progress: the fraction of its linked
  tasks in state `DONE` (0% with zero linked tasks). *(Added 2026-09-04, MX3.)*

**Scope boundary:** The manually set progress state and the derived task-completion
percentage are two independent figures — setting one never changes the other, and
neither is computed from the other. Linkage is task ↔ goal only, one goal per task
(a task cannot link to more than one goal), many tasks per goal, optional on both
sides. Deleting a goal does not delete its linked tasks; unlinking them happens first
implicitly, or the goal delete is blocked until they're unlinked — *(a build-time
default: deleting a goal clears the link on its tasks rather than blocking the
delete; flagged for confirmation, not yet product-owner approved)*. No numeric target
value, no milestones, key results, or check-in history, and no linkage to habits or
time in V1 — those remain out of scope pending further approval (Appendix A.2 item 5
still has milestones, icon, multiple category tags, and a derived status all
unapproved).

### 11. Daily review

- The user can complete a daily review for a chosen date by answering a fixed set of
  prompts with free text.
- The user can edit a previously completed daily review.
- The user can view a past daily review.
- While completing a daily review, the user can see that date's totals — actual time
  per category, and which habits were completed — for reference.

**Scope boundary:** One fixed prompt set, defined in the review SPEC, not editable by
the user. Answers are free text only — no ratings, scores, or structured fields. The
reference data is display-only. A review produces no follow-up actions or carry-over
items.

### 12. Weekly review

- The user can complete a weekly review for a chosen ISO week by answering a fixed set
  of prompts with free text.
- The user can edit and view a past weekly review.
- While completing a weekly review, the user can see that week's totals — actual time
  per category, habit completion counts, and the number of tasks that entered `DONE`
  that week — for reference.

**Scope boundary:** As for the daily review — one fixed non-editable prompt set,
free-text answers, display-only reference data, no generated output. Week boundaries
follow the ISO week resolved in the account's timezone.

### 13. Reports

The user can view each of the following reports over a user-chosen date range,
computed deterministically:

- **Time by category** — total actual time per category.
- **Planned vs actual by category** — planned total, actual total, and difference per
  category.
- **Habit completion** — for each habit, the number of completed days and the
  completion rate across the range.
- **Task throughput** — the number of tasks that entered `DONE` within the range.
- **Daily actual totals** — total actual time for each day in the range.

**Scope boundary:** This list is exhaustive for V1. No custom report builder, no
arbitrary group-by, no saved reports, no comparison between two ranges, no trend lines
or forecasts, no correlation between metrics. A frontend may render these as charts;
the underlying figures are fixed. As in §6, "time by category" and "planned vs actual
by category" attribute a task-linked block's time to its linked task's category, not
"Uncategorized" (§10).

### 14. Data export

- The user can export all of their data — categories, planned blocks, actual blocks,
  tasks, habits and their completions, goals, daily reviews, weekly reviews, and notes
  — in a single open, documented format, without contacting support. *(Notes added
  2026-09-05, MX4.)*

**Scope boundary:** Export is a full, user-initiated snapshot delivered as a download.
No scheduled export, no partial or filtered export, no import in V1, no delivery to a
third-party destination.

### 15. Notes

*(Added 2026-09-05, MX4 — product-owner approved. The reference screen
(`docs/design/screens/notes.md`) additionally shows tags, pin/favourite/archive/trash,
checklists-inside-notes, rich text, and related-notes links; none of those are
approved and none are built in V1. `docs/design/design-system.md` §6.4 had
separately, and independently of this approval, ratified Notes as "must not be
implemented" — that ratification predates this approval and needs reconciling with
the frontend agent; it does not override the product owner's decision here.)*

- The user can create a note with a title and a free-text body.
- The user can edit a note's title and body.
- The user can delete a note.
- The user can see all of their notes.

**Scope boundary:** Plain text only — no rich text, formatting, or embedded
checklists. No tags, no pin/favourite/archive states, no trash/soft-delete (delete is
permanent), no linkage to a category, task, habit, or goal, no related-notes feature,
no word/character count as a product requirement. A note has no due date and is never
part of a workflow — it is pure free-form capture.

## Non-functional requirements

### N1 — Architecture

A single deployable Go binary (modular monolith). PostgreSQL is the only datastore. No
message broker, cache, or search engine in V1.

### N2 — Cost

The deployed system, including database and hosting, runs within free tiers at the
expected load: on the order of tens of accounts, each with thousands of blocks, tasks,
and completions.

### N3 — Data isolation

Every read and write is scoped to the authenticated account. No interface the product
exposes lets one account observe or modify another account's data.

### N4 — Time and timezone correctness

Every instant is stored unambiguously. "A date" and "a week" are always resolved in the
account's timezone. Blocks that span midnight, and reports whose range crosses a
daylight-saving transition, produce correct totals.

### N5 — Web client

A modern web frontend, usable across current desktop and mobile browser viewport sizes
(responsive). No native mobile app, no offline mode, no installable-PWA requirement in
V1.

### N6 — Availability and durability

Best-effort availability appropriate to a personal tool on free infrastructure.
Regular database backups exist, and a restore has been performed successfully at least
once before V1 is considered done.

### N7 — Performance

Interactive views — a day's timeline, the board, a report over a one-month range —
respond within a small fraction of a second at the expected load. No numeric SLO beyond
"feels immediate for one user".

## V1 non-goals (explicit)

Deliberately excluded from V1. Items marked → V2 or → V3 are placed on the roadmap; the
rest have no committed home.

- Recurring tasks and any recurrence/scheduling engine → **V2**
- Reusable day-plan templates and "copy a previous day" → **V2**
- Importing time or events from an external calendar (e.g. Google Calendar) → **V2**
- Live timer / stopwatch capture of actual time → **V2 (candidate)**
- A wider or customizable analytics set; a custom report builder → **V2**
- AI-assisted planning, suggested schedules, pattern detection, recommendations → **V3**
- Auto-categorization or any "smart" default → **V3**
- Weekly / monthly / weekday-selective habit cadences; grace days; streak freezes → not committed
- A numeric/percentage goal-progress *target value* (distinct from the derived
  task-completion fraction, MX3); goal milestones; goals linked to habits or time →
  not committed
- Editable review prompt sets; ratings or scores in reviews → not committed
- Task subtasks, labels, estimates, attachments, comments, dependencies → not committed
- Task starred/pinned flag; a time-of-day component on a task's due date → not committed
- Configurable Kanban columns; multiple boards; WIP limits; swimlanes → not committed
- Category hierarchy, groups, merging, per-category budgets → not committed
- Email verification, password-reset email, OAuth / social login, MFA, self-service account deletion → not committed
- Any collaboration, sharing, teams, accountability, or social feature → **permanent non-goal** (see Vision)
- Native mobile app, offline mode, PWA install → not committed
- Notifications, reminders, email digests → not committed
- Data import; scheduled or partial export → not committed
- Real-time multi-device sync; websockets → not committed

### Resolutions

**Q6 — Password policy (resolved 2026-09-04, product owner).** A password must be **at
least 6 characters** (maximum 128, to bound password-hashing cost) and must contain **at
least one lowercase letter, at least one uppercase letter, and at least one special
character** (any character that is not a letter or a digit). No digit is required. No
denylist or breached-password check in V1. The policy is enforced at registration and at
password change.

**Q9 — Recording past-tense data for future dates (resolved 2026-09-04, product owner).**
The user **may** record actual time blocks, mark habit completions, and complete
daily/weekly reviews for dates that have not yet occurred. No "not after today" check is
applied. (The habit *current streak* still anchors on today/yesterday, so a future
completion does not inflate it.)

**Q11 — Habit archive/unarchive (resolved 2026-09-04, product owner).** Archiving a habit
hides it from the active list but **preserves all of its completion history**.
Unarchiving restores the habit with that history intact, so its streak resumes from the
stored completions.

**Q1 — Daily-review prompt set (resolved 2026-09-04, product owner — placeholder wording,
replace freely).** Fixed, non-editable, four prompts:

1. What went well today?
2. What didn't go as planned?
3. What will you do differently tomorrow?
4. One thing you're grateful for.

**Q2 — Weekly-review prompt set (resolved 2026-09-04, product owner — placeholder wording,
replace freely).** Fixed, non-editable, four prompts:

1. What were the highlights of this week?
2. What did you struggle with?
3. Did your time go where you intended?
4. What is the one priority for next week?

**Q3 — Export file format (resolved 2026-09-04, product owner).** A **single JSON
document** — one downloaded `.json` file containing every entity the account owns, as
named arrays keyed by entity type, with a documented schema (`docs/export-format.md`).
No CSV/archive format in V1.

**Q10 — "Tasks that entered `DONE` in a range" (resolved 2026-09-04, confirmed at M7).**
A **distinct task** count: a task with **one or more** `→ DONE` transitions whose `at`
falls inside the range counts **once**, however many times it entered and left `DONE`
within that range (`task_transitions.to_state = 'DONE' AND at ∈ [from, to)`, `count(DISTINCT
task_id)`). The transition time is recorded on every state change, including creation
(`from_state` null); this has been true since M3. Implemented identically by M6 (weekly
review reference data) and M7 (Task throughput report) — same query, same interpretation.
